# 全面审计 · 2026-08-01

范围:建单 → 生产 → 采购 → 财务 全链路。目标是**准确、无重复、无死环节**。

方法:不看感觉,看证据。三条线索交叉验证 ——
① 页面有没有入口能点到;② 功能背后的表有没有产生过数据;③ 同一个操作是不是被实现了多遍。

盘子大小:**80 个页面 / 61 个 API 路由 / 141 个 action 文件 / 167 个组件 / 158 张表**。

> ⚠️ 本文两处结论是我推翻自己后改的,见文末「我判错又改回来的」。
> 猜表名是本项目最容易翻车的地方,凡是"某表 0 行 ⇒ 功能没人用"的结论,都必须先确认代码读的**真**是那张表。

## 二、采购域有三张表同时装采购行 —— 最该收口的一处

| 表 | 行数 | 谁在写 |
|---|---:|---|
| `procurement_tracking` | **349** | `procurement-tracking.ts`、`procurement.ts` |
| `procurement_line_items` | 37 | `procurement-items.ts`、`procurement.ts` |
| `procurement_items` | 30 | `procurement-items.ts`、`procurement.ts` |
| `procurement_sheet_items` | **0** | `po-extract.ts` |

而 `updateProcurementItem` 这一个函数名,在 **三个文件里各有一份、签名互不相同**:

```
procurement-tracking.ts  updateProcurementItem(itemId, updates: {...})
po-extract.ts            updateProcurementItem(itemId, updates: Partial<{...}>)
procurement-items.ts     updateProcurementItem(itemId, orderId, fields: Record<string, any>)
```

`addProcurementItem` / `deleteProcurementItem` / `getProcurementItems` 同样在
`procurement-tracking.ts` 和 `procurement.ts` 里各有一份。

**这意味着"一条采购项"在系统里没有唯一定义** —— 从哪个页面进,写进哪张表、走哪套校验,是不一样的。
对账对不上、数量口径分叉、改了一处另一处不动,根源都在这里。

**建议**(需要你拍板,我没擅自改):以 `procurement_tracking`(349 行,数据最多)为主表收口,
`procurement_sheet_items` 直接废弃(0 行),另两张评估是并入还是各司其职。
这是本次审计里**唯一一个我认为值得专门排期做**的重构 —— 其余都是小手术。

## 六、我判错又改回来的(记录下来,防止下次再犯)

审计过程中我有三处结论是错的,靠核对代码**实际读的表**才纠正:

| 我一开始说 | 实际 |
|---|---|
| `/supervision` 督办是死页(`supervision_items` 0 行) | ❌ 错。它读的是 `milestones`/`orders`/`procurement_line_items`,**实时计算,是活的** |
| `/material-master` 物料主数据是死页(`materials` 0 行) | ❌ 错。真表是 `material_master`,**43 行**,活的 |
| `/inbox` 邮件看板是死页(`emails` 0 行) | ❌ 错。真表是 `mail_inbox`,**3456 行**,用得最重的功能之一 |

三次都是同一个错误:**我按业务名猜了表名**。这跟本轮之前踩的
`checklist_data` 是 JSON 字符串、风险标写进 `special_tags`、`allow_shipment` 全是补建默认值,
是同一类。**结论:任何"这个功能没人用"的判断,先把代码里那行 `.from('...')` 找出来看。**
