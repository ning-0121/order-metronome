## 0. 这一张要证明什么

不是"代码能跑",而是这句产品承诺:

> **跟单做完 BOM 后,不再需要知道采购系统下一步在哪个按钮;系统自己把正确的工作送到采购面前。**

如果这一点在真实员工手里成立,P0 才真正完成。

## 4. 跑一遍(真人操作,不要代跑)

1. 跟单在订单里录 BOM —— **故意留一个物料不填 consumption_basis**;
2. 点「提交采购」→ 期望看到 🟠 `NEEDS_BOM_CONFIRMATION`,**并点名到那个物料**;
3. 跟单补上口径,再次提交 → 期望看到 🟢 `系统已自动生成待采购需求(N 项)`;
4. 跟单**到此为止,不再点任何按钮**;
5. 采购登录,打开采购中心 → 期望第一眼就看到「待采购 N 项」。

第 4 步是整个 P0 的核心:**跟单不该知道「归并」这个词。**

---

## 5. 验收 8 项 —— 谁来判

```bash
npx tsx scripts/verify-procurement-p0-pilot.mts <订单号>
```

脚本**只读**,不写任何东西。它严格区分三类:

| # | 验收项 | 判定方 |
|---|---|---|
| 1 | 非 Pilot 单完全无变化 | 🧑 人工(找一张名单外的单,确认台账仍可新增) |
| 2 | basis 缺失停在 NEEDS_BOM_CONFIRMATION | 🧑 人工(看页面)+ 🤖 断言②(库里口径缺口数) |
| 3 | 不需要再找「归并」按钮 | 🧑 人工 + 🤖 断言⑥(MRP 与首个采购项相差 ≤120s = 同一次提交内自动完成) |
| 4 | 自动产生正确的 procurement_items | 🤖 断言④ |
| 5 | 数量与 BOM / consumption_basis 对账 | 🧑 **人工看对账表**(脚本打表不给结论,理由见下) |
| 6 | 采购页面出现「待采购 N 项」 | 🧑 人工 + 🤖 断言④ 的 N |
| 7 | 无孤儿 execution line | 🤖 断言⑦ |
| 8 | `lint:data-access` 保持 2324 不涨 | 🤖 `npm run lint:data-access` |

**为什么第 5 项不给机器结论**:`total_required_qty` 面料走「件数 × 大货单耗」、
客供/加工厂承担的行整行跳过 —— 它**不是** `Σ net_purchase_qty`。
在验收脚本里复刻一遍归并算法,就是造第二套真相,正是 ADR-006 要防的东西。
所以脚本只打出「物料 / 色 / 单位 / 总需求 / 建议采购 / 来源数」对账表,由跟单和采购看数字对不对。

脚本另外还断言了三条结构守恒(不重算数量):项数 ≤ 需求数、Σ来源数 ≤ 需求数(防重复计入)、
归并键唯一、无零来源项、无空数量项。

## 6. 一个现在还证明不了的不变量

> Pilot production `procurement_line_items` 一旦产生,100% 必须能反查 `procurement_item_id`。

**P0 阶段执行行本就为 0** —— 它们要等采购确认采购项之后才生成(自动确认 = 系统替人做商业承诺,违反 DP-4)。

所以现在断言⑦只能证明**入口被堵住了**(旧对账入口、legacy 台账桥、7 个 tracking writer 全部服务端硬拒绝),
不能证明生产数据最终满足这个不变量。**这一条要等 P1 采购确认跑通后复验。**

## 7. 完成标准

- 可断言项全部 PASS(脚本 exit 0);
- 人工三项确认成立;
- **跟单没有问过"接下来点哪里"**。

达成 → Production Gate PASS,再扩到 3–5 张。
任一断言 FAIL → `PROCUREMENT_GENERATOR_PILOT=off`,先停,不要扩大。
