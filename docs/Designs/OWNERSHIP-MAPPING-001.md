# OWNERSHIP-MAPPING-001 · 节点 owner_role 与实际职责不符

**状态**:登记(2026-08-17 CEO 裁定:本轮**不批量改模板**)
**类型**:责任配置缺陷(configuration defect),不是展示问题

---

## 触发案例

**1022927(QM-20260710-009,杭州杨小姐)**

| | |
|---|---|
| 逾期节点 | 尾期验货 |
| 系统里的 `owner_role` | **`sales`** |
| 业务的实际说法 | 「需要 QC 点击尾期验货」 |
| 逾期 | 10 天 |

业务批注和系统配置**指向两个不同的部门**。所以这条逾期无论催谁都不会动:
催业务 → 他做不了;而 QC 根本不知道有这件事。

## 为什么不现在批量改

看到一个例子就把所有 inspection 类节点批量改成 QC,是拿一个样本推断整张模板。
风险:
- 部分「验货」节点在某些流程里确实由业务发起(客户指定第三方验货等);
- 模板已版本化(V1 托底 / V2 标准 / V3 部门线),批量改会同时动到在途订单;
- 改 owner_role 会直接改变逾期归属与考核归属 —— 属于 KPI 影响面。

## 正确的后续做法(下一轮)

审 **模板层** 的 `step_key → owner_role` 映射,而不是手改单张订单:

1. 按模板版本(V1/V2/V3)导出全部 `step_key → owner_role`;
2. 与各部门实际职责逐条对表(QC/采购/财务/物流各自认领);
3. 分歧项由部门负责人拍板,写回模板定义;
4. 在途订单是否跟随修改,单独决策(默认不动,避免改变历史考核口径)。

## 本轮做了什么

- Overdue Attribution V1 的归属链是 `owner_user_id → owner_role → UNASSIGNED`,
  **忠实反映配置**:1022927 现在明确显示「责任=陈陈」(该节点的实际 owner),
  而不再笼统算给订单负责人。配置错就显示成错的 —— 这样它才会被发现和修掉。
- 生产实测 `UNASSIGNED`(既无人也无角色)**0 项** —— 说明当前问题不是"没分配",
  而是"分配到了错的部门",这类**无法靠归属链自动识别**,只能靠业务对表。
