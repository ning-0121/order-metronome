# 全面审计 · 2026-08-01

范围:建单 → 生产 → 采购 → 财务 全链路。目标是**准确、无重复、无死环节**。

方法:不看感觉,看证据。三条线索交叉验证 ——
① 页面有没有入口能点到;② 功能背后的表有没有产生过数据;③ 同一个操作是不是被实现了多遍。

盘子大小:**80 个页面 / 61 个 API 路由 / 141 个 action 文件 / 167 个组件 / 158 张表**。

> ⚠️ 本文两处结论是我推翻自己后改的,见文末「我判错又改回来的」。
> 猜表名是本项目最容易翻车的地方,凡是"某表 0 行 ⇒ 功能没人用"的结论,都必须先确认代码读的**真**是那张表。

## 二、采购三张表 —— 不是重复,是三层;真正的病在命名(2026-08-01 已处理)

> ⚠️ 本节整段推翻了初版。初版我写「三张表同时装采购行,建议以 procurement_tracking
> (349 行最多)为主表收口」。**两处都错了**:它们不是同一个东西的三份副本,
> 而 349 行也不代表它是主表 —— 恰恰相反,新表里有一列就叫 `legacy_tracking_id` 指向它。

### 它们是分层的

| 表 | 列数 | 职能 | 行数 | 覆盖订单 | 最后写入 |
|---|---:|---|---:|---:|---|
| `procurement_items` | 71 | 核料/归集:算需求、找供应商、报价、财务审批 | 30 | 5 | 2026-07-24 |
| `procurement_line_items` | 47 | 采购执行:实际下单、到货、催货 | 37 | 6 | 2026-07-27 |
| `procurement_tracking` | 21 | 采购台账:最简的「谁、什么料、几号到」 | 349 | **87** | **今天,近30天 +64** |
| `procurement_sheet_items` | — | (随报价器一同废弃)| 0 | 0 | — |

### 真实状况:完整流水线试点 5-6 张单就停了,全公司还在用最简台账

`legacy_tracking_id` 只有 **1 行**有值 —— 新旧迁移**根本没发生过**。
采购中心那套核料 → 执行的完整设计(71 列 + 47 列,含报价、财务审批、催货)
只在 7-10 到 7-27 之间试点了 5-6 张单,之后停了。
而 87 张单的实际采购,一直记在那张 21 列的台账上,今天还在写。

**这不是技术债,是流程没落地。** 往哪个方向收是业务决策,代码层面替不了。

### 病在命名 —— 已修

三个文件里有**同名不同表**的函数,这才是"对账对不上、口径分叉"的直接原因:

| 函数名(改前) | 在哪 | 实际操作的表 |
|---|---|---|
| `getProcurementItems` / `add` / `update` / `delete` | `procurement-tracking.ts` | `procurement_**tracking**` |
| `getProcurementItems` / `delete` | `procurement.ts` | `procurement_**line_items**` |
| `updateProcurementItem` | `po-extract.ts` | `procurement_**sheet_items**`(0 行) |

**没有一个真的操作 `procurement_items`**(那张归 `procurement-items.ts`)。
名字全指向第三张表,谁 import 都可能拿错。

已做:
· `procurement-tracking.ts` 全组改名为 `*TrackingRow`(名副其实),文件头写清三表分工;
· 删掉 `po-extract.ts` 里那个 37 行的死函数(写 0 行废表、无任何调用方);
· 采购域重名导出**清零**;
· 新增 `tests/procurement-table-ownership.test.ts` 钉住纪律:
  采购 action 之间不许重名导出、台账文件不许写另外两张表、废表和报价器不许复活。

### 订单详情页的「采购进度」页签也按数据说话了

那个页签里原本写死:`SupplyChainTab`(执行明细)置顶并标「单一真相」,
`ProcurementTrackingTab`(台账)默认折叠、标「仅补充说明,真实进度以上方为准」。
按上表,**87 张单里有 81 张**,跟单点开看到的是个空的「真相」面板,真数据被折叠在下面。
——这和建单页把从没建过单的 PO 模式标成「主路径」是同一个毛病。

改成按本单实情排版:哪块有数据哪块在上面、默认展开;两块都有数据时给一条口径不一致的提醒。
不替任何一方站队,等流程定了方向再收掉另一块。

## 七、报价器下线(2026-08-01 已执行)

CEO 拍板「报价器,不留」。落地时发现它不是一个孤立功能,而是**一整条从头到尾零使用的平行建单链**:

```
报价器 quoter_quotes 0  →  客户PO customer_po 0  →  ?po=  →  建单页「PO 模式」
```

`?po=` 只有客户PO页会传,而客户PO必须先选一张已审批报价。源头一断,整条链永久不可达。
与此同时,真正在用的是手工录入表单:**orders 202 张,全部走它**。

而建单页的模式切换器上写的是:

> 本订单系统以 **PO 驱动** 为主路径(订单从已审批报价快照派生)。手工录入为 **legacy 回退** 模式。

**方向写反了** —— 把一张单都没建过的链标成主路径,把承载全部业务的表单标成"回退"。
按钮上甚至就写着「从 PO 创建(暂无 PO)」。这大概是同事觉得建单流程绕的原因之一。

已删:`app/quoter/`(4 页)、`app/customer-po/`、`app/actions/quoter.ts` / `quoter-training.ts`、
`POOrderForm`、`order-from-po`、`order-intake-read`、`/api/os/ignite-po`、夜间 cron 的报价训练同步、
导航记录;建单页双模式切换器收敛为唯一表单(保留了那条救过命的套装数量提醒)。
数据库删表 6 张(迁移带自证守卫:非空则中止)。

**没删**:`lib/quoter/*`(纯类型与算料函数)—— 仍被 `lib/po/types.ts`、`lib/order/from-po.ts` 引用,
清理它是独立的第二步。以及 `order_customer_pos`(6 行,多客户PO合单容器)和
`app/actions/customer-po.ts`(订单附件版本管理)—— 名字像,其实是另一回事,都在用。

> ⚠️ 更正本文第三节的一处错误:我原写「报价器挂在导航栏,同事天天看得见」。
> **不对** —— 2026-07-31 就已加了 `dormant` 机制,导航渲染时 `filter(l => !l.dormant)` 把它过滤掉了,
> 它当时是「路由还在、入口已收起」的状态。
