# 审批与通知送达 · 全面审计(2026-08-06)

> 触发:CEO 报「菁菁的免罚申请查一下午没收到」+「采购显示待财务审批,财务系统看不到」。
> 结论:两案背后各有一个**结构性缺陷**,均已修复上线并补发积压。

## 案一:全站 37 处审批通知被 RLS 静默拒收(P0,已修)

- `notifications` 表 RLS INSERT 策略 = `auth.uid() = user_id`,登录用户只能给**自己**发通知
- 全站 37 处(18 个文件)审批/催办代码用**申请人的 session** 给审批人插通知 → 全部被拒
- `.insert()` 返回的 error 无一处检查 → 静默失败数月
- 为何没被发现:预算审批/邮件摘要恰好用了 service-role(能到),"有的能收到"掩护了"大部分收不到"
- 企微推送同病:`pushToUsers` 用 session 读别人的推送凭据,RLS 下读空 → 推送为零

**修复**:统一入口 `insertNotifications()`(service-role + 必查 error);37 处全部替换;
`pushToUsers` 内部改 service-role;新静态闸 `lint:notif` 进 `npm run check` 防回潮。

## 教训(进 CLAUDE.md 语料)

1. **service-role 与 session 的边界必须显性**:给别人写数据的一律走统一入口
2. **吞 error 是万恶之源**:RLS 拒收不抛异常,只在返回值里 —— 不查即盲
3. **"有的能到"比"全都不到"更危险**:部分成功掩盖系统性失败
4. **对接上线要带存量迁移**:新事件流不会自动覆盖旧数据
